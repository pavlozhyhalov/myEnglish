# Резервні копії myEnglish

Дві незалежні лінії захисту. Після разового налаштування (розділ 3) нічого робити вручну не треба: копії робляться, перевіряються й пильнуються самі, про збій приходить push.

## 1. Копія всередині Supabase (працює з 2026-11-28)
- **Щоночі ~02:17 UTC** pg_cron викликає функцію `backup`: знімок усієї бази (таблиці `public`, акаунти `auth.users` з хешами паролів, `auth.identities`, перелік файлів) → gzip → **AES-256-GCM** → приватний бакет `backups`:
  `daily/<дата>.meb` — 7 днів, `weekly/<дата>.meb` (щопонеділка) — 28 днів.
- Для чого: швидко повернути дані однієї людини чи таблиці (помилка в коді, щось стерлось). Не рятує, якщо зник сам проєкт Supabase — для цього лінія 2.

## 2. Копія поза Supabase — Cloudflare R2 (як у Resonance, але зашифровано)
GitHub Actions, `.github/workflows/db-backup.yml`:
- **Щоночі ~03:41 UTC** — повний `pg_dump` бази (дані, схема, політики RLS, функції, акаунти) → gzip → **gpg AES-256** → R2:
  `db/backup-<дата>.sql.gz.gpg` — 14 днів, `weekly/…` щопонеділка — 35 днів. Після завантаження розмір у R2 звіряється.
- **Файли** (голосові в чатах, кліпи «тоді й зараз», скріншоти звернень) — дзеркало `files/<бакет>/…`: нове докачується, видалене в застосунку зникає й тут (Політика: видалений акаунт стирається).
- **Щонеділі** `.github/workflows/db-restore-test.yml` бере останню копію, розшифровує й **відновлює в тимчасовий Postgres** (робоча база не зачіпається), рахує рядки головних таблиць. Порожньо → «копія непридатна» → push.

Пильнування:
- кожне завдання звітує функції `backup` → `#/admin` → «Резервні копії» (коли, розмір, скільки рядків відновилось);
- збій → push адміністраторам + запис у журнал помилок;
- щоденний автомонітор (функція `push`) пише, якщо копія в Supabase старша за 2 дні, копія поза Supabase — за 50 год, перевірка відновлення — за 9 днів.

Логи GitHub Actions публічні (репозиторій відкритий): у них лише розміри й «є дані / порожньо», без даних і шляхів файлів.

**Зберігання (Політика приватності — «до 35 днів»):** в Supabase 28 днів, у R2 35 днів; файли — дзеркало без історії.

## 3. Разове налаштування лінії 2 (≈ 15 хв, робить власник)
Поки секретів немає, завдання зелені й нічого не роблять.

1. **Cloudflare** (безкоштовно; той самий акаунт, де купуватимете домен):
   - R2 → Create bucket → назва, наприклад, `myenglish-backups`, регіон EU (Location hint: Eastern Europe або «EU jurisdiction»);
   - R2 → Manage API tokens → Create API token → права **Object Read & Write**, лише цей бакет → скопіювати Access Key ID і Secret Access Key;
   - Account ID — на головній сторінці R2 праворуч.
   Безкоштовно до 10 ГБ; у нас зараз ~1 МБ бази + ~50 МБ файлів.
2. **Supabase** → Project Settings → Database → Connection string → **Session pooler** (порт 5432), підставити пароль бази (якщо не пам'ятаєте — там же «Reset database password»; на роботу застосунку не впливає).
3. **GitHub** → репозиторій → Settings → Secrets and variables → Actions → New repository secret:

| Секрет | Звідки |
|---|---|
| `SUPABASE_DB_URL` | крок 2 (спецсимволи в паролі — `@`→`%40`, `#`→`%23`) |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | крок 1 |
| `R2_BUCKET_NAME` | `myenglish-backups` |
| `BACKUP_PASSPHRASE` | `#/admin` → «Резервні копії» → «Ключ розшифрування» |
| `OFFSITE_SECRET` | `#/admin` → «Резервні копії» → «Поза Supabase: як увімкнути» |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Project Settings → API Keys → service_role (лише для копії файлів) |

4. GitHub → Actions → **DB backup to R2** → Run workflow, потім **DB restore test** → Run workflow. За кілька хвилин у `#/admin` три зелені рядки.

**Ключ.** `BACKUP_PASSPHRASE` розшифровує обидві лінії. Він у Vault Supabase і в секретах GitHub (звідти його не прочитати, але завдання відновлення ним користуються). Збережіть його ще й у менеджері паролів — це єдиний ручний крок, один раз.

## 4. Відновлення
**Дані однієї людини чи таблиці (лінія 1):**
1. `#/admin` → «Резервні копії» → завантажити файл.
2. `node scripts/backup-decrypt.js daily-2026-11-28.meb <ключ> backup.json`
3. `node scripts/backup-restore-sql.js backup.json --user <uuid>` (або `--table public.cards,public.mistakes`, або все) > `restore.sql`
4. Виконати в Supabase → SQL Editor. Вставляються лише відсутні рядки (`on conflict do nothing`), тригери перевірок на час транзакції вимкнено. Перевірено 2026-11-28 на живій базі з відкатом.

**Увесь проєкт зник (лінія 2):**
1. Новий проєкт Supabase (EU).
2. Завантажити з R2 `db/backup-<дата>.sql.gz.gpg`, розшифрувати:
   `gpg --decrypt backup-<дата>.sql.gz.gpg | gunzip > dump.sql` (пароль — `BACKUP_PASSPHRASE`).
3. `psql "<рядок Session pooler нового проєкту>" -f dump.sql` (клієнт PostgreSQL 17). Помилки про вже наявні ролі й розширення Supabase — нормально.
4. Файли: `aws s3 sync s3://myenglish-backups/files/<бакет> ./<бакет> --endpoint-url https://<account_id>.r2.cloudflarestorage.com` → завантажити в однойменні бакети.
5. Задеплоїти функції, повернути секрети функцій, вписати новий URL і ключ у `js/config.js`. Паролі учнів працюють — хеші є в копії.

## 5. Що не входить у копії
- **Секрети функцій** (`GEMINI_API_KEY`, `ALLOWED_USERS`, ключі APNs, VAPID у `app_keys` — VAPID є в копії бази): тримайте в менеджері паролів.
- **Кеш озвучення** `tts` — створюється заново сам.
- **Код, міграції, зміст** — у GitHub.
