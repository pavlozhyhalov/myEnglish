# Витік чи інцидент з даними — що робити (GDPR ст. 33–34)

**Інцидент** — будь-яке випадкове чи незаконне знищення, втрата, зміна, розголошення персональних даних або доступ до них: витік ключа (service_role, GEMINI_API_KEY, ключ копій), помилка RLS, загублений ноутбук із копією, злам акаунта адміністратора, файл з даними в публічному місці.

## Перша година
1. **Зупинити:** змінити скомпрометований ключ (Supabase → Project Settings → API Keys / Database password; секрети функцій; `backup_key` / `offsite_secret` у Vault — новий через `vault.update_secret`; токени Cloudflare R2; секрети GitHub). Вимкнути вразливу функцію або політику.
2. **Зберегти сліди:** знімок логів (Supabase → Logs: API, Postgres, Functions; GitHub Actions; `client_errors`), час виявлення.
3. Записати в журнал інцидентів (таблиця нижче — копіювати в приватне місце, **не в цей публічний репозиторій**).

## До 72 годин — оцінити й повідомити
- **Наглядовий орган** (у Польщі — UODO: uodo.gov.pl → «Zgłoś naruszenie», онлайн-форма), якщо ризик для прав людей не малоймовірний. Якщо не всі відомості є — повідомити частинами.
  Зміст: що сталося, які категорії й скільки людей і записів, наслідки, вжиті заходи, контакт.
- **Самих людей** (ст. 34) — без зайвої затримки, якщо ризик високий (паролі, листування, голос, відомості «Про вас»): push + лист + банер у застосунку простою мовою: що сталося, що ми зробили, що робити їм (змінити пароль).
- Не повідомляти органу можна, якщо ризик малоймовірний (наприклад, дані були зашифровані, а ключ не витік) — але **записати в журнал рішення й обґрунтування**.
